# Данные структуры реестра

Единственный источник — предоставленный файл **15092026_структура для подготовки мока данных.xlsx**, лист **провалидирированные и принятые**, диапазон **A1:M2278**. В нём 2 277 строк данных и 13 колонок. Названия, владельцы КП и процессов, коды и связи перенесены из этой таблицы. Руководители блоков и ССП добавлены отдельно как демонстрационные ФИО по запросу пользователя. Прежние числа из сводной таблицы, данные PDF и публичные интернет-источники больше не используются.

## Иерархия и подсчёт

Иерархия согласована с пользователем: **Блок продукта → ССП продукта → Продукт → Связанные процессы**. Первые два уровня берутся из колонок A и B. Поля блока и ССП внутри записи процесса берутся из H и I: они отражают принадлежность самого процесса и могут отличаться от ветки продукта.

Процесс идентифицируется по коду из колонки K: пробелы удаляются, буквы приводятся к верхнему регистру. Учитываются только коды вида «П» и цифры. Один код соответствует одному объекту записи независимо от числа продуктов и клиентских путей.

При сравнении текстовых полей удаляются только пробелы в начале и конце. Исходные значения без этой обработки сохранены в снимке. Поэтому 199 различных исходных написаний названий КП дают 198 названий после удаления краевых пробелов; одинаковые названия КП с разными написаниями внутри строки автоматически не объединяются.

В продукте повторное вхождение того же процесса через разные КП учитывается один раз. На уровне ССП и блока считается **объединение уникальных процессов потомков**, а не сумма их счётчиков. Один процесс может относиться к нескольким продуктам и нескольким блокам продукта. Поэтому сумма счётчиков блоков — 1 093, а число уникальных процессов во всей модели — 913. Обе величины имеют разный смысл.

233 процесса связаны с несколькими продуктовыми узлами, 122 — с несколькими блоками продукта. У каждого канонического продукта проверена принадлежность к единственной паре «блок продукта, ССП продукта»; пересечений между ветками для одного ключа продукта нет.

## Ключи продуктов и расхождения источника

Для продукта используется валидный GUID из колонки D. При отсутствии GUID используется числовой ID из C. Если оба идентификатора не установлены, создаётся отдельная служебная группа внутри исходного блока и ССП; она помечена `isPlaceholder: true` и сохраняет название из E.

В 258 строках UID пустой. Ещё 103 строки содержат текстовые заглушки идентификатора: 72 строки «нет связи с продуктом» и 31 строка «требуется уточнить». Эти строки сохранены. Они образуют 11 служебных групп в своих исходных ветках и не включаются в число 87 идентифицированных продуктов.

У СберПрайм ID 2063 и 2064 имеют одинаковый GUID и одинаковое название. Они объединены в один продукт по GUID. Оба исходных ID сохранены в `productIds`; расхождение отражено в `sourceIssues`.

У 18 корректных кодов встречается несколько названий: П3216, П1339, П1045, П3446, П3354, П1125, П3461, П3949, П4052, П3655, П4071, П2753, П2526, П3770, П3924, П1659, П3399, П3827. У продукта ID 14522 также два названия: «Управление запусками NBA» и «Инструменты развития NBA». Для отображения используется наиболее частое исходное название; при равной частоте — порядок сравнения строк для русского языка. Это техническое правило отображения, а не утверждение об актуальности одного варианта. Все варианты и номера исходных строк сохранены в `titleAliases`/`nameAliases`, `sourceRows` и `sourceIssues`.

Конфликтов владельцев, блоков и ССП для одного корректного кода процесса не обнаружено. Принадлежность по блоку продукта не заменяет принадлежность самого процесса.

- Строка 2117: вместо кода записано «не существует»; владелец, блок и ССП процесса содержат `#N/A`.

Именно поэтому 915 различных значений колонки K дают 913 корректных кодов. Продукты ID 178 «Розничное взыскание и урегулирование» и ID 14546 «Управление взысканием проблемных активов сегмента ММБ» оставлены в дереве с нулём корректных процессов.

## Владельцы и отсутствующие поля

Владелец процесса берётся из J. У продукта показаны уникальные владельцы связанных КП из F: один ФИО либо число владельцев, полный список в `owners`. В исходнике нет отдельного владельца продукта, руководителя блока или ССП. Это подтверждают все 13 заголовков снимка: поля владельцев есть только для КП (F «Владелец клиентского пути») и процессов (J «Владелец процесса»).

По запросу пользователя для **9 блоков и 38 ССП — всего 47 узлов** — вместо заглушки добавлены вымышленные полные русские ФИО. Они детерминированно вычисляются из стабильного идентификатора узла и не меняются при перезагрузке. У этих узлов указаны `ownerSimulated: true`, `ownerRole: 'Руководитель'`, а `owners` содержит одно демонстрационное ФИО. Это примеры для интерфейса, а не сведения о фактическом руководстве. Владельцы КП у продуктов и владельцы процессов из Excel сохранены без изменений; фильтрация процессов по владельцу продолжает использовать исходное поле J.

В исходнике нет даты создания, статуса, типа, тегов и числа вариантов процесса. Для совместимости с интерфейсом записаны `date: ''`, `status: 'Не указан'`, `type: ''`, `tags: []`, `count: 0`, `delta: 0`. Эти значения означают отсутствие сведений, а не фактический статус или показатели процесса. Дата 2026-09-15 хранится только как дата снимка по имени файла и не является датой создания процесса.

## Демонстрационная эффективность

### Средняя оценка в аккордионах (24.09.2026)

Индикатор средней эффективности использует те же отфильтрованные записи, по которым построены сегменты. Формула: `E = Σ eᵢ / N`, где `eᵢ` — числовая оценка уникальной сущности от 0 до 100, `N` — число оценённых сущностей. Эквивалентная запись по сегментам: `E = Σ (nⱼ × Eⱼ) / Σ nⱼ`, где `Eⱼ` — среднее **реальных демонстрационных оценок** внутри сегмента, а не условная середина диапазона. Дополнительные бизнес-веса не вводились.

Неоценённые (`null`) не входят в числитель и знаменатель. Оценка `0` — полноценное измерение, а не отсутствие оценки. Нет оценённых — нет средней оценки («—»). Округление до целого применяется только при отображении числа со знаком %; исходные оценки сохраняются. Подсказка также показывает целые проценты, без десятичного знака. Цвет стандартной сферы эффективности определяется по неокруглённому среднему и действующим порогам шкалы (≤45, >45–65, >65–85, >85), а не по промежуточному значению счётчика. Положение шторки также соответствует неокруглённой оценке; при 100 шторки нет.

Одна сущность учитывается один раз на уровне текущей ветки, даже если входит в несколько продуктов. Нельзя усреднять средние дочерних аккордионов с их общими количествами: множества процессов пересекаются. При смене таба метрика соответствует выбранной сущности: процессы или клиентские пути. Оценки КП в текущем наборе сгенерированы отдельно; это не среднее их входящих процессов. Все оценки по-прежнему демонстрационные, не данные фактической эффективности.

Все 2 277 ячеек колонки M «Эффективность процесса» пусты. По согласованному запросу эффективность смоделирована для демонстрации интерфейса. Исходное отсутствие оценки сохраняется в `sourceEfficiency: null`, демонстрационное значение помечено `efficiencySimulated: true`.

Значение детерминированно вычисляется по коду процесса. Профиль распределения зависит от исходного блока самого процесса. Поэтому одна запись имеет одинаковые эффективность и цвет во всех продуктовых ветках, а повторная загрузка не меняет набор.

| Группа | Порог по последней методологии пользователя | Цвет |
| --- | --- | --- |
| Лидеры | Более 85% | `#34c759` |
| On track | Более 65%, до 85% включительно | `#6155f5` |
| Есть отставания | Более 45%, до 65% включительно | `#ffcc00` |

Шаг числовых оценок — 0,1 процентного пункта. Счётчики цветовых групп считаются по уникальным процессам узла. Общая шкала `maxima` равна максимумам пяти групп среди блоков и сохраняется при раскрытии: **[120, 60, 126, 77, 35]**.

В режиме **«Сравнение с лидером» (Structure Chart 1)** подложка каждой группы пропорциональна её `maxima` относительно суммы максимумов. Полезная ширина пяти подложек — 331 px, промежутки — 4 × 8 px. Заполненная часть равна отношению счётчика к соответствующему `maxima`, умноженному на ширину подложки. Масштаб фиксирован для всей выбранной сущности и не меняется при фильтрации или раскрытии.

В режиме **«Соотношение эффективности» (Structure Chart 2)** подложек и лидерских максимумов нет. Ширина каждой диаграммы — 364 px; после вычитания промежутков по 4 px оставшееся место распределяется пропорционально значениям сегментов. Высота цветных блоков — 22 px. Нулевые сегменты не занимают места, диаграмма с нулевой суммой остаётся пустой. Цвет «не оценивались» в этом компоненте — `#c4c4c4`, по макету Chart 2. Узкие сегменты не увеличиваются ради подписи: значение остаётся в подсказке и доступном описании. Тумблер выключен для «Соотношения эффективности», включён для «Сравнения с лидером»; по умолчанию сохранён Chart 1.

## Локальные файлы и контракт

`structure-source.js` — компактный снимок всех исходных строк: словарь строк и матрица индексов, где −1 означает пустую ячейку. Он загружается перед `structure-data.js`. Снимок не редактирует исходный Excel и не обращается к внешним системам. `import-structure-source.py` читает Excel без изменения и печатает обновлённый снимок в стандартный вывод.

`window.BPM_STRUCTURE` содержит `roots`, `nodes`, `records`, `colors`, `maxima`, `total`, `sources`, `pathCount`, `relationCount`, `pathRelationCount`, `productCount`, `productNodeCount`, `placeholderCount`, `sourceFile`, `sourceSheet`, `sourceDate`, `sourceRowCount`, `sourceIssues` и `provenance`. `productCount` исключает служебные группы, `productNodeCount` включает их.

`roots`, `nodes` и `children` ссылаются на одни объекты узлов. Все узлы содержат `records` — объединение уникальных канонических объектов процессов своего поддерева. Поле `record.products` содержит названия связанных продуктов, `productLinks` — их идентификаторы и метаданные. `record.source` и `node.source` равны `xlsx`.

В интерфейсе необходимо сообщать, что эффективность и ФИО руководителей блоков/ССП являются демонстрационными. Число процессов, названия, связи и владельцы КП/процессов берутся из предоставленной таблицы. Исходный Excel и `structure-source.js` при добавлении демонстрационных руководителей не изменялись.

## Режим клиентских путей

### Двустороннее раскрытие и демонстрационные типы участия

В режиме «Клиентские пути» ссылка с количеством раскрывает связанные процессы. В режиме «Процессы» аналогичная ссылка раскрывает все клиентские пути процесса. Используется одна и та же совокупность **2 169 уникальных связей КП ↔ процесс** из Excel; обратный список не ограничивается текущим продуктом и не создаёт новых связей. Каждый процесс включён хотя бы в один КП; максимум в текущем снимке — 47 КП у процесса П1339. В любом вложенном списке до 50 записей включительно пагинации нет, свыше 50 используется общий Table/Pagination.

В Excel нет признака участия **«Основной / Дополнительный»**. По разрешению пользователя от 23.09.2026 эти теги заполнены **демонстрационно**, отдельно для каждой связи: процессы КП упорядочены по исходному числовому ID, каждая четвёртая связь обозначена «Дополнительный», остальные — «Основной». Это не фактическая бизнес-классификация. Значения не меняются при сортировке, фильтрации или повторном открытии страницы; пояснение есть в подсказке тега и примечании интерфейса. У клиентских путей в обратном списке такие теги не выводятся.

Обратный индекс и демонстрационные поля `relationshipType` / `relationshipSimulated` создаются в слое отображения `structure.js`. Канонические записи, поле `type`, исходные массивы `linkedProcesses` и снимок Excel остаются неизменными. Полные КП не записываются внутрь процессов, чтобы не создавать циклических ссылок и не влиять на экспорт.

`window.BPM_STRUCTURE_PATHS` — отдельная проекция того же снимка для иерархии **Блок продукта → ССП продукта → Продукт → Клиентский путь**. Она предоставляет тот же контракт `roots`, `nodes`, `records`, `colors`, `maxima`, `total` и метаданные источника. Узлы и массивы статистики созданы отдельно от `BPM_STRUCTURE`; идентификаторы соответствующих узлов и исходные владельцы сохранены. Данные, идентификаторы и статистика 913 процессов не изменяются.

Каноническая запись КП определяется точным названием из G после удаления только краевых пробелов. Получено **198 КП и 212 уникальных связей продукта с КП**. Одинаковый КП под несколькими продуктами используется как один объект. Счётчики ССП и блоков — объединения уникальных КП потомков. Продуктовая иерархия по-прежнему включает 9 блоков, 38 ССП, 87 идентифицированных продуктов и 11 служебных групп. Владелец КП берётся из F; конфликтов владельца, блока или ССП для одного названия в этом снимке нет.

В Excel **нет ID клиентского пути**. `record.id` вида `structure-kp-…` — технический стабильный ключ по названию. `number` и `code` вида `КП-ДЕМО-0108` — демонстрационные номера по алфавитному порядку названий; указаны `numberSimulated: true` и `sourceNumber: null`. Номера сохраняются при перестановке или повторении строк снимка, но могут измениться при добавлении новых названий. ID продукта из C не выдаётся за ID КП.

`linkedProcesses` содержит канонические объекты связанных процессов из `BPM_STRUCTURE`; `linkedProcessIds` и `linkedProcessCodes` — их технические ключи и исходные коды. `processCount` и совместимое поле `count` считают различные корректные процессы одного КП. Всего 2 169 уникальных связей КП с процессом; 2 171 связь продукта, КП и процесса. `sourceRows` и `sourceLinks` сохраняют все 2 277 исходных строк, их продуктовую принадлежность, владельца и исходное значение кода процесса. В семи строках без корректного кода `processId: null` и `validProcessCode: false`: они не создают фиктивный процесс, но сохраняют КП в дереве. Два КП «Урегулирование проблемной задолженности ФЛ» и «Урегулирование проблемной задолженности ЮЛ» имеют ноль корректных процессов.

Эффективность КП отсутствует в источнике и смоделирована независимо по идентичности названия: `sourceEfficiency: null`, `efficiencySimulated: true`. Пороги и цвета совпадают с методологией процессов: >85%, >65–85%, >45–65%, ≤45%, `null`. Статистика и масштаб пересчитаны по уникальным КП; `maxima` режима КП — **[33, 25, 15, 9, 10]**. Цвет одного КП одинаков во всех ветках и не меняется при повторной загрузке или перестановке строк.

Проверки `test-structure-paths-data.cjs` сопоставляют записи КП с исходными строками, владельцами и кодами процессов, проверяют объединения по всей иерархии, сохранение строк без процесса, детерминированность и неизменность полного исходного объекта `BPM_STRUCTURE`.
